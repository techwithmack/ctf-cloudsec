# Challenge 2 player passwords: how they work, history, and decisions

Last verified live: **2026-10-16**. Read this before touching `CTF_PLAYER_PASSWORD`,
`random_password.player`, or how players are told how to log in.

## TL;DR

- **Default / current behavior (same as DEF CON, Aug 2026):** every team gets its **own random
  16-character Forgejo `player` password**, generated by Terraform at provision time. Teams never
  share a password, and an old team's password does not work on a new team.
- The `CTF_PLAYER_PASSWORD` repo variable is **unset** and must stay unset for this behavior. It is
  an *optional override* that forces one shared password onto every team (see
  [The optional override](#the-optional-override-ctf_player_password)).
- In GitHub Actions logs the password is **masked (`***`)**. Nobody reading the logs, including the
  Cloud Village's bridge, can see it. Someone with AWS/Terraform access reads it from state (below).
- **Unresolved:** the repo contains no mechanism that *delivers* a team's password to its players.
  See [Open question](#open-question-how-players-actually-got-passwords-at-def-con).

## How it works (mechanics)

| Step | Where |
|---|---|
| Password generated, one per team workspace | `random_password.player` in `challenge-2-iac/main.tf` |
| Passed to the Forgejo container as `PLAYER_PASSWORD` | ECS task definition env in `challenge-2-iac/main.tf` |
| `player` account created on first boot (write access to the one `infra` repo) | `challenge-2-iac/forgejo/bootstrap.sh` |
| Exposed as a sensitive Terraform output `player_password` | `challenge-2-iac/main.tf` |
| Printed by the provision script, **masked in CI** via `::add-mask::` | `scripts/add-team.sh` |

Each team has its own Terraform workspace (`team_id`), so each has its own `random_password`.
A re-apply of an existing team does not rotate it; destroying and re-provisioning a team generates a
new one (and a fresh EFS volume).

### Reading a team's password

```bash
cd challenge-2-iac
terraform init                      # once, uses the shared S3 backend (needs AWS credentials)
terraform workspace select <team_id>
terraform output -raw player_password
```

Requires AWS credentials for the CTF account. Players' environments live in `us-west-2`.

## Why the override exists, and why it is NOT in use

Cloud Village's Lambda dispatches `provision-teams.yml` itself and only gets URLs back. Cloud
Village **declined a callback/webhook** (Discord, 2026-10-01), and the workflow deliberately masks
passwords in logs because the repo is public. So the bridge has no way to *receive* a random
per-team password. `CTF_PLAYER_PASSWORD` was added so one known value could be pasted into the CTFd
challenge text.

We decided **not** to use it: it trades per-team passwords for one shared secret that is visible to
every player and every repo collaborator, and it needs someone to edit CTFd text by hand. If the
override is set, `team_id` is the *only* thing separating teams, so `team_id`s must be unguessable.

Never derive a password from `challenge_request_id` (or any value shown in run names): the repo is
public and that value appears in the run title.

## The optional override: `CTF_PLAYER_PASSWORD`

- Repo variable (Settings → Secrets and variables → Actions → Variables). Min 12 characters.
- **Set** = every team provisioned afterwards gets that password. Existing teams keep theirs.
- **Unset / deleted** = per-team random (current, DEF CON behavior).
- Set: `gh variable set CTF_PLAYER_PASSWORD --body '<value>'`; remove: `gh variable delete CTF_PLAYER_PASSWORD`.

## Verified live, 2026-10-16

Provisioned two throwaway teams (`pwa1`, `pwb1`) through the real `provision-teams.yml` workflow
with the variable unset:

- Both provisioned successfully on the `aikidolabs.net` domain.
- Actions logs showed `Password: ***` and `Flag: ***` for both (masked).
- `terraform output -raw player_password` returned a **16-character** password for each, and the
  two **differed**.
- Each team's own password logged in to its own Forgejo (HTTP 200).
- Team A's password on team B's Forgejo: **401**. The old shared value: **401** on both.
- Both teams were destroyed afterwards. (Earlier the same day, a full solve of both challenges was
  run on a separate throwaway team, including the Challenge 2 `deploy/*` OIDC escalation.)

## Open question: how players actually got passwords at DEF CON

Nothing in the repo delivers a team's password to its players. At DEF CON (`3fbbefe`) the password
was masked in CI and only readable from Terraform state, so a person with AWS access had to read it
and pass it on, or the logins were handed out out-of-band. **We could not determine which from the
repo.** If this was a manual step, it is still manual. Record the answer here once known:

> _DEF CON delivery method: (unknown, fill in)_

If a no-human, no-shared-secret delivery is wanted, the least invasive option identified is a
custom Forgejo sign-in banner (written by `forgejo/bootstrap.sh` from the container's own
`PLAYER_PASSWORD`) so each team sees its own login on its own team URL. This would require rebuilding
and pushing the Forgejo image. **Not built.** The security boundary would be the same as the shared
password's (anyone with the team URL gets in), so `team_id`s must be unguessable either way.
